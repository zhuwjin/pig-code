> Goal: build a graphical AI Code Agent desktop app from scratch with Rust + [gpui-kit](https://gpui-kit.com/) (0.6),
> with the UI benchmarked against [ZCode](https://zcode.z.ai/cn/docs/agents) (Z.ai's Agentic Development Environment),
> and the architecture modeled on the mature open-source implementations under the local `agent-workspaces/` directory: codex / kimi-code / opencode.

## 1. Research Conclusions

### 1.1 gpui-kit capability assessment (verdict: strong match; two gaps need in-house work)

gpui-kit 0.6 clearly ships purpose-built components for chat/agent scenarios — the vast majority of a ZCode-style UI has off-the-shelf parts:

| UI requirement | gpui-kit component | Verdict |
|---|---|---|
| Virtualized chat-history list | `MessageScroller` (variable-height virtualization, follow-tail, re-measuring row heights as the stream grows) | ✅ purpose-built |
| Message bubble | `Message` + `Bubble` (avatar/header/footer slots, alignment, variants) | ✅ purpose-built |
| Streaming Markdown | `TextView` (CommonMark+GFM, tree-sitter highlighting, `push_str` incremental append, `stream_fade` fade-in) | ✅ killer feature; the official `examples/stream-markdown` is a ready-made template for render-as-SSE-arrives |
| Composer @file /command $skill chips | `InlineToken` of `Input`/`Textarea` (atomic inline tokens; the official story's comment literally reads "A chat composer") | ✅ purpose-built |
| Command palette | `Command` (grouping/filter/shortcuts/keyboard navigation) | ✅ |
| Three-pane layout | `Dock` (draggable/serializable) or `Resizable` + `Sidebar` | ✅ |
| Code block/editor | `Editor` (rope-backed 200k lines, read-only mode, decorations) | ✅ |
| Attachment chips / Toast / Dialog / Skeleton / Shimmer / Tabs / Tooltip | `Attachment` / `Notification` / `Dialog` / `Skeleton` / `ShimmerText` etc. | ✅ |
| **Diff view** | no ready-made component | ⚠️ **in-house**: start from a read-only `Editor` + `tree-sitter-diff` highlighting of unified diff text; later draw add/delete line backgrounds with decorations |
| **Terminal emulator** | no ready-made component | ✅ already built in-house and landed (2026-10-04): `portable-pty` + `alacritty_terminal` + a custom-drawn Element; see that day's entry at the end of this file |

Other key facts:

- `gpui-kit = "0.6"` is the umbrella crate; `gpui_kit::*` re-exports gpui itself (the Apache-2.0 snapshot of zed's gpui, `gpui-pre`). **Always go through crates.io; never git-depend on zed's gpui** (it would pull in GPL-3.0 crates).
- Async: gpui ships an smol-based executor (`cx.spawn` / `cx.background_executor()`); the dependency tree already includes reqwest/tokio, with the official built-in `gpui-pre-reqwest-client`.
- Windows build requirements: Win10+, VS 2022 C++ workload, cmake; graphics backend wgpu (DX12 on Windows, no Vulkan SDK needed).
- The dev profile needs `opt-level = 3` on the gpui-family crates, otherwise debug rendering is noticeably slow.
- APIs will keep changing through 0.x → pin the version and follow the changelog.
- Zed's `crates/agent_ui` is the best interaction reference, but **read the design only, never copy the code** (agent_ui is GPL-3.0).

### 1.2 Reference architectures (from codex-rs / opencode / kimi-code)

The three implementations converge on the same architectural consensus:

1. **Contract first**: converge "everything the UI can see" into a standalone protocol/schema package.
   - codex-rs: `codex-protocol` (`Op`/`EventMsg` envelope + ~90 event variants); between UI and core sits a further stable app-server JSON-RPC v2 projection.
   - opencode: `packages/schema` (Effect Schema); the dependency direction is explicitly constrained by its AGENTS.md: the client never depends on core/server.
   - kimi-code: `packages/transcript` (an isomorphic rendering data layer: `transcript.reset` full snapshot + `transcript.ops` idempotent deltas + seq).
2. **Commands go request-response; state flows through an append-only event stream**; events carry a seq, and replay cursors recover state after disconnection.
3. **Delta events are separated from durable events**: streaming fragments like `text.delta` serve immediate rendering only and are never persisted; `text.ended` carries the full final value as the replayable boundary (a mature design in opencode's `session-event.ts`).
4. **Permissions = pending requests in the event stream**: core emits an approval-request event and blocks waiting; the UI unblocks it with a reply command carrying the same id (codex's `ExecApprovalRequest ↔ Op::ExecApproval`; opencode's Deferred + reply endpoint).
5. **Session persistence = JSONL**: codex rollout (SessionMeta on the first line, one item per line after) + a sqlite index; history is rebuilt on resume.

**Why not reuse codex-rs core directly**: although it is Apache-2.0 and offers an `InProcessAppServerClient` embedding path,
(a) that version's `WireApi` only speaks the Responses protocol — **no Chat Completions** — which is awkward against GLM/DeepSeek/Kimi and other OpenAI-compatible endpoints;
(b) ~100 path-dependency crates unpublished to crates.io, so you can only git-depend on the whole repository, at prohibitive follow cost;
(c) building the core ourselves is the primary learning goal. Verdict: **borrow the design, build our own engine**.

## 2. Overall Architecture

### 2.1 Process model

**Single process, dual execution domains** (following kimi-code's "transport isomorphism" idea — a desktop app just doesn't need HTTP):

```
┌─────────────────────── Pig Code (single process) ─────────────────────┐
│  UI domain (gpui main thread + smol     │  Agent domain (tokio runtime │
│  executor)                              │  thread)                     │
│                                         │                              │
│  pig-app                                │  pig-core                    │
│  · three-pane layout / message stream / │  · Session / Turn loop       │
│    composer                             │  · Provider (SSE streaming)  │
│  · events → view-state reduce           │  · tool execution / approval │
│  · approval popup → reply Op            │    gate                      │
│       ▲                                 │  · rollout JSONL persistence │
│       │  Event stream (async-channel)   │        ▲                     │
│       └────────────┬────────────────────┘        │ Op (mpsc)           │
│                    └─────────────────────────────┘                     │
│                    contract = pig-protocol (pure serde types; both      │
│                    sides depend on it)                                  │
└─────────────────────────────────────────────────────────────────────────┘
```

- **pig-protocol** (dependency-free logic, types only): `Op` (UI→core commands), `Event` (core→UI events), message/item models. Both UI and core depend only on it; core imports no gpui types.
- **pig-core**: runs on a dedicated tokio runtime thread (reqwest/SSE/tool subprocesses all need tokio; gpui's smol executor can't run the tokio ecosystem). Exchanges `Op`/`Event` with the UI over `async-channel` (compatible with both the smol and tokio sides).
- **pig-app**: gpui-kit GUI. A `cx.spawn` loop reads the Event channel and `update`s each Entity's view state.
- This boundary later yields "remote core" capability for free (just swap the channel for a WebSocket), and naturally supports "one GUI managing several concurrent tasks".

### 2.2 Protocol design (first draft)

```rust
// pig-protocol: UI → core
enum Op {
    NewSession { cwd: PathBuf },
    SendMessage { session_id, content: Vec<UserContent>, mode: ExecMode },
    Interrupt { session_id },
    ApprovalReply { request_id, decision: ApprovalDecision }, // allow / always allow / deny
    SetModel { provider, model },
    Compact { session_id },
}

// pig-protocol: core → UI (seq monotonically increasing, replayable)
enum Event {
    SessionConfigured { session_id, cwd, model },
    TurnStarted { turn_id },
    TextDelta { item_id, delta },            // live-only
    TextDone { item_id, full_text },         // durable boundary
    ReasoningDelta / ReasoningDone,
    ToolCallBegin { item_id, tool, input_summary },
    ToolCallOutputDelta { item_id, delta },  // live-only
    ToolCallEnd { item_id, result, is_error },
    PatchBegin { item_id, files },
    PatchEnd { item_id, diff: FileDiff },
    ApprovalRequested { request_id, kind: Exec|Patch, detail }, // core blocks awaiting ApprovalReply
    ContextUsage { used, total },
    TurnComplete { usage, duration },
    TurnAborted,
    Error { message },
}
```

Key points: delta and Done are separated (opencode pattern); approval requests carry a `request_id` paired with the reply command (codex pattern); all events carry `session_id + seq` for future UI replay after reconnect.

### 2.4 Key technical decisions

| Decision point | Choice | Rationale |
|---|---|---|
| Model protocol | **OpenAI Chat Completions + SSE** (own `ModelProvider` trait, Anthropic implementation reserved) | GLM/DeepSeek/Kimi/Qwen are all compatible; codex's Responses-only is the cautionary tale |
| core↔UI transport | in-process `async-channel` (not HTTP) | zero overhead for a single-process desktop app; the contract is already guaranteed by pig-protocol, swappable for WS later |
| Streaming Markdown | `TextViewState::push_str` + `stream_fade` | official and ready-made; no patching of unclosed syntax ourselves |
| File-edit tool | **start with a search/replace-style `Edit` (old_string/new_string)**; codex's `apply_patch` format optional later | Claude Code-family models adapt best to the Edit format; the apply_patch parser can be ported from codex later (Apache-2.0) |
| Diff view | read-only `Editor` + `tree-sitter-diff` highlighting unified diff → later decorations for per-line backgrounds | gpui-kit has no diff component; this is the biggest in-house piece |
| Terminal | **a real terminal has landed** (2026-10-04): portable-pty + alacritty_terminal drawn in-process in the GUI, bypassing pig-core; webview+xterm.js was dropped (uncontrollable render/input pipeline, big binary) | an embedded local shell in the agent panel is a hard requirement; command execution is still rendered as tool cards (both paths coexist) |
| Session persistence | JSONL (codex-rollout style: meta on the first line + one item per line) | simple, append-only, naturally resume-friendly |
| Approval model | core emits the event and **blocks** for the UI reply; the four exec-mode tiers decide which tools skip approval | the model jointly validated by codex/opencode |
| License red line | `gpui-kit` from crates.io only; zed `agent_ui` is read-only, never copied | avoid GPL-3.0 contamination |

### Suggested cadence
M0→M2 is the steepest learning curve (the gpui mental model + the tokio/smol bridge + SSE parsing); suggest **doing a spike of each first**:
1. Get `examples/stream-markdown` running and change it to read SSE (half a day; validates the streaming pipeline);
2. A minimal tokio-thread + channel + gpui-update demo (half a day; validates the dual execution domains).
Start M0 formally only after both spikes pass.

## 4. Key Risks

| Risk | Mitigation |
|---|---|
| gpui-kit 0.x API churn | Pin `=0.6.x` patch versions; read the changelog before upgrading; copy the official stories for component usage wherever possible |
| The Windows build chain (VS2022 C++/cmake/wgpu-DX12) | Get the official `story` gallery running before starting; `script/install-window.ps1` |
| tokio ↔ smol dual-runtime bridge bugs (deadlock/lost events) | One-directional channels; the UI side only `try_recv`/`await`, never blocking the main thread; the M2 spike validates first |
| Streaming Markdown performance in long sessions | `TextView` incremental re-parsing is already the official approach; chunk messages into multiple items to avoid a single over-long TextView |
| Context-window management | Before M5 only truncation warnings; compact copies opencode/codex's summary prompts |
| Scope creep (ZCode's feature surface is enormous) | Stick strictly to the milestones; all of P2 deferred; build "a usable M3" before talking differentiation |
